# CONTRIBUTING Guidelines  
*Standards for contributing to the KAIROX humanitarian blockchain initiative.*

---

## 1. Overview  
Thank you for your interest in contributing to KAIROX.  
This document outlines the official contribution process, coding standards, documentation rules, and expectations for all contributors.  
All contributions must follow these guidelines to maintain the integrity, security, and professionalism of the project.

---

## 2. How to Contribute  
You can contribute in several ways:  
- Submitting pull requests  
- Improving documentation  
- Reporting issues  
- Proposing governance improvements  
- Assisting with mission operations  
- Contributing to smart contract development  
- Supporting community initiatives  

Before contributing, please review:  
- [SECURITY.md](./SECURITY.md)  
- [CODE_OF_CONDUCT.md](./CODE_OF_CONDUCT.md)  
- [GOVERNANCE_FRAMEWORK.md](./GOVERNANCE_FRAMEWORK.md)

---

## 3. Branching Model  
KAIROX uses a simple and clear branching strategy:  
- **main** — production‑ready code and documentation  
  https://github.com/kairoxtime/kairox/tree/main  
- **dev** — active development  
  https://github.com/kairoxtime/kairox/tree/dev  
- **feature/\*** — new features or documents  
  https://github.com/kairoxtime/kairox/tree/feature  
- **fix/\*** — bug fixes or corrections  
  https://github.com/kairoxtime/kairox/tree/fix  
- **docs/\*** — documentation updates  
  https://github.com/kairoxtime/kairox/tree/docs  

All pull requests must target the **dev** branch unless explicitly approved otherwise.

---

## 4. Pull Request Requirements  
Every PR must include:  
- A clear description of the change  
- A reference to any related issue or proposal  
- Clean, readable commits  
- No unrelated changes  
- No secrets, private keys, or sensitive data  
- Passing tests (if applicable)  
- Updated documentation when needed  

PRs that do not meet these requirements will be rejected.

---

## 5. Commit Message Standards  
KAIROX uses an official institutional commit message format to ensure clarity, consistency, and professional documentation across the project.

**Format:**  

    type: description

**Examples:**  

    add: new mission template
    update: governance framework links
    fix: incorrect internal path in README
    docs: improve contributor guidelines

Commit messages must be:  
- lowercase  
- concise  
- factual  
- free of emojis  
- free of marketing language  

---

## 6. Documentation Standards  
All documentation must follow these rules:  
- Use Markdown (.md)  
- Use clear, concise language  
- Use relative internal links  
- Use consistent headings  
- Include the official footer at the bottom of every document  

Official footer:  

    Prepared by O. KAIROX — Founder
    KAIROX — Humanitarian Blockchain Project
    © All Rights Reserved

---

## 7. Code Standards  
For smart contracts and programs:  
- Follow Solana development best practices  
- Use clear variable names  
- Avoid unnecessary complexity  
- Include comments for critical logic  
- Avoid unsafe patterns  
- Never commit private keys  
- Ensure all programs are testable  

All code must pass security review before merging.

---

## 8. Issue Reporting  
When opening an issue:  
- Use a clear title  
- Provide steps to reproduce  
- Include expected vs actual behavior  
- Attach logs or screenshots if relevant  
- Tag the issue appropriately  

Security issues must **not** be reported publicly.  
Use the process in [SECURITY.md](./SECURITY.md).
